# AgentFlow RL v3: veRL rewrite specification

Implementation status: complete locally; the pinned Linux CUDA smoke commands
are documented in the root README.

## Goal

Build an independent veRL v0.8.0 implementation of one reusable AgentFlow
optimization framework across four terminally verifiable environments:

1. preserve the original AgentFlow role loop and shared-memory semantics;
2. express each task through its action schema, tools, environment, and terminal evaluator;
3. run a frozen AgentFlow baseline;
4. add LoRA only to Planner next-step generation;
5. collect groups of complete trajectories for each query;
6. compute terminal-reward population-normalized advantages at trajectory level;
7. expand each trajectory advantage to its real Planner turns;
8. optimize each Planner turn with the asymmetric turn-level GSPO objective.

GSM8K and Ticket preserve the verified v2 tasks. DeepResearch and Coding test
the same optimization method on longer-horizon search and executable-code tasks.

Planner checkpoints start directly from the selected Qwen checkpoint. Query
Analyzer, Executor, Verifier, Generator, Base Generator, tools, and task
environments remain frozen during RL.

## Version boundary

- veRL tag: `v0.8.0`
- veRL commit: `7aed6b230776f963fa09509c10d9c3a767d1102c`
- trainer entrypoint base: `verl.trainer.main_ppo_sync`
- rollout backend: vLLM
- actor backend: FSDP with PEFT LoRA
- orchestration: Ray + veRL ResourcePool/WorkerGroup/TransferQueue

The commit pin is intentional: veRL AgentLoop, TransferQueue, and trainer APIs
are not treated as a floating dependency.

## AgentLoop output contract

One complete trajectory may contain one to three Planner turns. The task loop
returns a list:

```text
[
  AgentLoopOutput(turn 0 prompt/response token IDs),
  AgentLoopOutput(turn 1 prompt/response token IDs),
  AgentLoopOutput(turn 2 prompt/response token IDs, reward_score=trajectory reward),
]
```

Each output contains only the tokens generated by the trainable Planner:

- `prompt_ids`: exact chat-template input for that Planner call;
- `response_ids`: exact generated IDs, including EOS when emitted;
- `response_mask`: one for every Planner response token;
- `response_logprobs`: rollout-engine log probabilities;
- `extra_fields`: query/trajectory/turn identity, action, tool result, validity,
  terminal reason, and task verification.

Frozen-model tokens are never placed in `response_mask` and cannot receive a
gradient.

## Reward and advantage hierarchy

veRL keys have the form `{uid}_{session_id}_{turn_index}`. For every uid:

1. select only the final output of every valid session;
2. read its binary trajectory reward;
3. compute mean and population standard deviation across valid sessions;
4. use zero advantage for zero-variance groups;
5. exclude infrastructure-invalid sessions from mean/std;
6. broadcast the session advantage to all its Planner-turn outputs.

Thus a multi-step trajectory enters reward mean/std exactly once. Turn
flattening occurs only afterward.

## Update hierarchy

The actor receives all real Planner-turn rows from the collected query batch as
one logical mini-batch. `ppo_epochs=2` reuses that frozen rollout batch for two
optimizer updates. `old_log_probs` are computed once by the veRL actor training
engine before both epochs.

The policy loss uses:

- `loss_mode=gspo`;
- `clip_ratio_low=0.001`;
- `clip_ratio_high=0.003`;
- no KL reward and no KL loss;
- temperature 1.2 in rollout and actor log-prob computation;
- top-p 1.0, disabled top-k, repetition penalty 1.0;
- one veRL sequence row per Planner turn.

## Runtime flows

### GSM8K

```text
Frozen Query Analyzer
  -> Planner turn
  -> legacy_llm Executor or deterministic dispatch
  -> Calculator
  -> Frozen Verifier
  -> judge feedback in next Planner memory
  -> Frozen direct Generator
  -> binary numeric-match reward
```

Formal baseline/train/eval use `legacy_llm`; smoke uses `deterministic`.

### Ticket

```text
Frozen Query Analyzer
  -> Planner turn
  -> Frozen Executor
  -> isolated stateful ticket tool environment or Frozen Base Generator
  -> shared Memory
  -> Frozen Verifier
  -> repeat until Verifier STOP or the step limit
  -> Frozen Generator
  -> deterministic binary verifier
```

Direct is Update -> Finish. Indirect is Query -> Update returned ticket ->
Finish. Finish records the domain submission; Verifier controls the loop. Every
AgentLoop session creates a fresh environment.

### DeepResearch

```text
Frozen Query Analyzer
  -> Planner turn
  -> Frozen Executor
  -> local BM25/Lucene Search, Read, or Frozen Base Generator
  -> shared Memory
  -> Frozen Verifier
  -> repeat until Verifier STOP or the step limit
  -> Frozen Generator with citations
  -> deterministic answer/supporting-fact evaluation
```

### Coding

```text
Frozen Query Analyzer
  -> Planner turn
  -> Frozen Executor
  -> code write, public tests, or Frozen Base Generator
  -> shared Memory
  -> Frozen Verifier over revision-bound test evidence
  -> repeat until Verifier STOP or the step limit
  -> Frozen Generator
  -> isolated hidden-test evaluation
```

## Two-GPU remote topology

The reference topology uses 2x A800 80 GB:

- GPU 0: external frozen OpenAI-compatible vLLM server;
- GPU 1: veRL FSDP LoRA actor plus colocated vLLM Planner rollout;
- Ray sees only GPU1 for the veRL job;
- frozen calls use the GPU0 HTTP endpoint.

This topology avoids loading the frozen subagent model inside every Ray worker
and preserves the original frozen/trainable model separation.

## Non-goals

- no TRL dependency;
- no LangGraph runtime dependency;
- no token-level GRPO objective;
- no whole-trajectory GSPO ratio;
- no training of frozen subagents;
- no SFT, critic, reference-policy KL, real ticket backend, or multimodal path.
